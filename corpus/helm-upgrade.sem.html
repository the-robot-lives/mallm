helm upgrade — install, configure, and release

Install the Helm CLI the way your OS packages it, know where repositories and kubeconfig live on each platform, and run idempotent helm upgrade --install releases with values files, namespaces, history, and rollback.

Helm is a CLI, not a daemon — nothing to enable. Install it, check helm env for the config dir, then helm upgrade --install myapp ./chart -n apps --create-namespace: it installs the release if absent and upgrades it otherwise, leaving a revision you can roll back with helm rollback. Install: brew install helmsudo apt-get install helm (baltocdn repo) or sudo dnf install helmwinget install Helm.Helm Target the cluster: kubectl config current-context shows the context helm will use Release: helm upgrade --install myapp ./chart -n apps --create-namespace -f values.yaml

Below: per-OS install paths and config locations (XDG dirs on macOS and Linux versus %APPDATA% on Windows), the Helm 2 versus 3 model, version-guarded flags, the upgrade flag reference table, and an agent runbook with expected output.

 Install the helm CLI per OS helm install brew apt baltocdn dnf winget scoop

Goal: get the helm binary on PATH from the platform package manager.

Homebrew: brew install helm — binary at /opt/homebrew/bin/helm (Apple Silicon) or /usr/local/bin/helm (Intel).

Debian/Ubuntu via the baltocdn repo: curl -fsSL https://baltocdn.com/helm/stable/debian/all.repo.txt | sudo tee /etc/apt/sources.list.d/helm-stable-debian.list, then sudo apt-get update && sudo apt-get install helm. Fedora: sudo dnf install helm from the official repos. Binary lands at /usr/bin/helm.

Winget: winget install Helm.Helm (Scoop alternative: scoop install helm). helm.exe lands on PATH — confirm with where helm from cmd.

No package manager or a pinned version: fetch the tarball — curl -fsSL https://get.helm.sh/helm-v3.16.1-linux-amd64.tar.gz | tar xz and move the unpacked helm to /usr/local/bin/.

 Find helm config and kubeconfig per OS helm env repositories.yaml kubeconfig xdg appdata

Goal: know which files helm reads for repositories, plugins, and the cluster connection — helm runs no service; these files are its entire OS footprint.

Run helm env: repositories live at ~/Library/helm/repositories.yaml (helm honors macOS XDG defaults) with cache under the same root. Cluster access is the kubeconfig at ~/.kube/config; override per command with --kube-context.

helm env reports XDG paths: ~/.config/helm/repositories.yaml (honor XDG_CONFIG_HOME if set) and cache at ~/.cache/helm/repository. Kubeconfig: ~/.kube/config or KUBECONFIG when set.

Helm stores under %APPDATA%\helm\ — repositories.yaml and plugins live there; verify with helm env. Kubeconfig: %USERPROFILE%\.kube\config. PATH from the winget install already covers helm.exe; nothing to enable at boot.

Helm 2 versus Helm 3

Helm 3 model: no Tiller, no helm init. Releases are stored as secrets in the release namespace, RBAC comes straight from your kubeconfig, and helm upgrade --install is the one idempotent command for both first deploy and update.

Legacy Helm 2: Tiller must be running server-side (helm init, often with --tiller-namespace in RBAC clusters) before any upgrade. Migrate to Helm 3 — the 2.x line is end-of-life and upgrade paths run through helm 2to3.

Helm 3.2.0+ adds --take-ownership to upgrade: adopt resources that exist in-cluster but are missing the Helm release annotations instead of failing the release.

Helm 3.8.0+ enables OCI registries by default: pull or upgrade straight from oci://registry.example.com/charts/myapp with a version tag, after helm registry login.

Upgrade flag reference

Flag | Meaning --install | Install the release if it does not exist, upgrade otherwise -f, --values FILE | Layer a values file (repeatable; later files win) --set key=val | Override a single value on the command line --reuse-values | Reuse the release's last values when upgrading --reset-values | Reset values to just what this command supplies --wait | Block until pods are ready or the timeout hits --atomic | Roll back automatically if the upgrade fails --take-ownership | Adopt unannotated existing resources (3.2.0+) -n, --namespace NS | Target namespace; pair with --create-namespace --kube-context NAME | Operate on a context other than the current one

Agent release runbook

Run an idempotent release and roll it back helm upgrade install rollback history agent expected-output

Goal: deploy or update a chart release from a local chart directory, read the revision from output, and prove rollback works — exact commands and expected output.

Run helm version --template '{{.Version}}'. Expected: v3.16.1 — a v3 semver, exit 0; v2 output means the legacy server-side flow applies instead. Run helm upgrade --install demo ./chart -n apps --create-namespace. Expected first run: Release "demo" does not exist. Installing it now. then a status block with NAME: demo, NAMESPACE: apps, STATUS: deployed, REVISION: 1; exit 0. Run the same command again after a chart change. Expected: Release "demo" has been upgraded. and the status block now shows REVISION: 2; exit 0. Run helm history demo -n apps. Expected: a table of revisions 1..N with STATUS deployed/failed; then helm rollback demo 1 -n apps returns the release to revision 1 (a new revision is created, it does not rewind time).

Failure mode: Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress means a release never completed — inspect helm history demo -n apps and clear the pending one with helm rollback demo N -n apps before retrying.
