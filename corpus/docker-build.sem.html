docker build — engine install, daemon, and builds

Install Docker Desktop or Docker Engine for your OS, keep the daemon running through the platform service manager, then build images with docker build and buildx — including the BuildKit output format to expect per version.

Install Docker Desktop on macOS and Windows (brew install --cask docker / winget install Docker.DockerDesktop), enable the systemd service on Linux, then build with docker build -t name:tag .. Docker 23.0+ uses BuildKit by default, so expect #1 [internal] load build definition output, not Step 1/N. Below: per-OS install paths, real service management (launchd-backed Desktop on macOS, systemd unit on Linux, the com.docker.service Windows service plus WSL2 backend), daemon.json locations, Windows feature-channel differences, and the version guards for BuildKit and buildx.

 Install the Docker engine per OS docker install desktop engine winget brew apt dnf wsl2

Goal: get the docker CLI talking to a running engine with the OS-native packaging.

Homebrew cask installs Docker Desktop: brew install --cask docker, then launch it once from /Applications and grant the privileged-helper prompt. The app drops docker, docker-compose, and docker buildx CLI symlinks under /usr/local/bin on first run.

Docker's repo script installs docker-ce plus buildx and compose plugins: curl -fsSL https://get.docker.com | sh. On apt systems that is the docker-ce package family; on dnf systems the docker-ce-stable repo. Add yourself to the group so sudo is not needed: sudo usermod -aG docker $USER, then re-login or newgrp docker.

Winget: winget install Docker.DockerDesktop. The Desktop requires the WSL2 backend — install it first with wsl --install --no-distribution and reboot when prompted. Scoop users: scoop install docker adds the CLI only; the Desktop install is still needed for the engine.

Windows 11 24H2: the WSL2 kernel ships in-box. After installing Docker Desktop, confirm with wsl --status that the default version is 2 and docker version answers.

Windows 11 23H2: update the WSL2 kernel before the Desktop install — wsl --update — or the engine can fail to start with a plumbing/WSL error.

Windows 10 22H2 (build 19045): supported by current Docker Desktop, but WSL2 must be enabled explicitly — wsl --install --no-distribution — and a reboot is required before the engine starts.

Older Windows 10 builds: current Docker Desktop releases are not supported (19044 is the floor). Use a Linux VM as the build host instead of an unsupported in-place upgrade.

 Keep the daemon running per OS docker daemon service systemd launchd com.docker.service

Goal: start the engine at boot and check its health the way each OS manages services.

Docker Desktop is a login app, not a unit you enable: start it with open -a Docker; its launchd helpers (com.docker.vmnetd and friends) load at install time. Wait for the whale menu-bar icon, then docker version reports the server. Logs: ~/Library/Containers/com.docker.docker/Data/log/.

systemd owns the engine: sudo systemctl enable --now docker starts it now and at boot. Health: systemctl status docker; logs: journalctl -u docker -f; after a daemon.json edit: sudo systemctl restart docker.

The Windows service com.docker.service (Docker Desktop Service) must be running and set to Automatic — check with Get-Service com.docker.service. The engine itself lives in WSL2 distros (docker-desktop); if builds hang, wsl --shutdown then restart the Desktop.

 Point the daemon at the right config file docker daemon.json config settings desktop

Goal: edit daemon settings (registry mirrors, log drivers, data-root) in the file your OS actually reads.

Edit /etc/docker/daemon.json directly, validate with dockerd --validate --config-file /etc/docker/daemon.json, then sudo systemctl restart docker.

The engine runs inside the Desktop VM: open Docker Desktop, Settings, Docker Engine, and edit the JSON there — it persists to ~/Library/Group Containers/group.com.docker/settings.json. Apply & Restart from the UI; there is no host-level /etc/docker.

Same Desktop UI path as macOS. On disk the Desktop keeps state under %APPDATA%\Docker\ — settings-store.json on Desktop 4.35 and newer, settings.json before that; edit through the UI, not the file, to avoid being overwritten.

Build output per version

BuildKit is the default builder: builds print #1 [internal] load build definition from Dockerfile style progress and finish with an exporting to image block. Do not set DOCKER_BUILDKIT=1 on 23.0+ — it is already on; the env var only matters on older engines.

Legacy builder: output is Step 1/4 : FROM alpine:3.20 lines. Prefix BuildKit explicitly with DOCKER_BUILDKIT=1 docker build ... to get cache mounts and parallel stages.

The buildx plugin ships with the CLI: use docker buildx build --platform linux/amd64,linux/arm64 -t user/app:1.0 --push . for multi-architecture images from one command.

Agent build runbook

Build an image and verify it runs docker build verify agent expected-output buildkit

Goal: from a directory with a Dockerfile, build a tagged image, prove it runs, and clean up — with exact commands and expected output.

Run docker version --format '{{.Server.Version}}'. Expected: a semver line such as 26.1.4, exit 0. An error template or exit 1 means the daemon is down — start it per the service how-to before building. Run docker build -t mallm-demo:1.0 .. Expected on 23.0+: BuildKit lines starting #1 [internal] load build definition from Dockerfile ending with exporting to image and naming to docker.io/library/mallm-demo:1.0; exit 0. Run docker run --rm mallm-demo:1.0. Expected: the image entrypoint output, exit 0. Run docker image rm mallm-demo:1.0. Expected: Untagged: mallm-demo:1.0 then Deleted: sha256:..., exit 0.

Failure mode: failed to solve: ... no such file or directory during #1 [internal] load build definition almost always means the build context directory is wrong — the Dockerfile path is resolved relative to the context, not the shell cwd of the agent.
